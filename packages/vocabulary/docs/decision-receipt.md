# Decision receipt terms

Name what a signed record of one allow-or-refuse decision carries, so a party that does not trust the decision point can check what it decided over, in what world and as one of how many. The [README](../README.md) is the short version of the repository; this page covers the `decision_receipt` section, added in 0.10.0.

Every term is a state a verifier derives from which fields a record carries and what they equal. One rule runs through all of them: an absent field and an empty one are different claims, and a zero-filled digest is never a stand-in for either. All terms are `proposed`, list no issuer and carry a `check`.

## The terms

| term | what it names | check |
|---|---|---|
| `decision_verdict` | the outcome for one action, in a fixed strictness order | the strictest verdict wins, the same way in every verifier; an empty set, an unregistered verdict and a differently spelled one are never read as allow; a two-valued deny is read as block |
| `request_commitment` | whether the decision is bound to the bytes of the request it judged | a digest that is not null, not empty and not zero-filled; an omitted one is reported as uncanonicalizable |
| `policy_commitment` | whether the record names the policy configuration the decision point applied | same digest rules; an omitted digest is not committed |
| `trust_root_commitment` | whether the record names the set of roots the decision point trusted | same digest rules; the digest is over the sorted root set |
| `revocation_list_in_force` | which revocation data the decision point held | a digest with a version, a digest without one, or neither; a list that revoked nothing still has a digest and is never no list loaded |
| `receipt_chain_link` | whether a record names the record its signer emitted before it | order, duplicate, fork and reset are refused or reported; the end is not established without a head anchor held outside the signer's reach |
| `possession_proof` | whether an allow carries the holder's proof of possession | an allow without one is refused; one proof carried by two allows is a replay |
| `decision_code` | a canonical kebab-case reason for a refusal | required on a refusal, absent on an allow, never free text or an argument |
| `enforcement_point_label` | a human label for an enforcement point | descriptive only; the signing key is the identity |
| `correlation_handle` | a host identifier that matches a record to the host's own logs | never an identity; a repeated handle is not a replay |
| `upstream_receipt` | one fact about a call, re-checkable at the provider that served it | the provider, its call id and an https re-check address; only an agreeing record is a pass |

## The values

| term | values |
|---|---|
| `decision_verdict` | `allow`, `constrain`, `require_approval`, `block`, `halt` |
| `request_commitment` | `committed`, `uncanonicalizable` |
| `policy_commitment` | `committed`, `not_committed` |
| `trust_root_commitment` | `committed`, `not_committed` |
| `revocation_list_in_force` | `versioned_list`, `unversioned_list`, `no_list_loaded` |
| `receipt_chain_link` | `first`, `linked`, `unchained` |
| `possession_proof` | `bound`, `absent` |
| `upstream_receipt` | `agrees`, `disagrees`, `unreachable`, `not_checked` |

`decision_code`, `enforcement_point_label` and `correlation_handle` take free values under the rules in their checks.

## Verdict order

`allow` < `constrain` < `require_approval` < `block` < `halt`, least to most strict. `constrain` means the decision point rewrites the action and binds the rewritten bytes. `halt` ends the run. The normative resolver, with its conflict vectors, is in the admission package: [VERDICT-PRECEDENCE](https://github.com/probityai/agent-evidence-vectors/blob/main/packages/admission/docs/VERDICT-PRECEDENCE.md).

## Deriving a value

`agent_evidence_vocabulary.registry` derives each value from a decision record:

```python
from agent_evidence_vocabulary import registry

registry.request_commitment({}).value                                   # 'uncanonicalizable'
registry.request_commitment({"requestHash": "0" * 64}).reason           # 'requestHash-zero-filled'
registry.revocation_list_in_force({}).value                             # 'no_list_loaded'
registry.decision_code({"verdict": "block", "code": "Denied: /etc"}).reason   # 'code-not-canonical'
registry.upstream_receipt(upstream, None).value                         # 'unreachable'
```

`receipt_chain_link(records, anchor=None)` walks a stream in emission order; a record's digest is the SHA-256 of its canonical JSON.

## Vectors

`vectors/decision-receipt/manifest.json` holds a positive and a negative case for every derived term. It is generated by `scripts/gen_decision_receipt_vectors.py`; `scripts/test_decision_receipt.py` regenerates it, compares, and runs every case through `registry.py`. Signature verification of a possession proof and the fetch of an upstream record are the verifier's own steps; the vectors fix the shape rules and what a verifier does with the answer.
