# Artifact binding for agent-evaluation records, version 1

Status: proposed. This document is a versioned contract of its own. It is not
part of the Adversarial Execution Evidence (AEE) predicate and it does not
change any AEE version. It sits beside AEE in this repository because it is
consumed by the same relying parties and tested by the same kind of corpus.

The claim this contract supports, stated once, in the words a producer may
publish:

> This record binds a Harbor result to the saved artifacts and grading inputs
> it names. It supports integrity checking and auditable regrading. It does
> not, by itself, attest that the original agent execution was genuine or
> completely observed.

Everything below either implements that sentence or bounds it.

## 1. Why this is not part of AEE

The AEE predicate describes what a containment substrate observed while it ran
a subject artifact, and it deliberately stops there. The vendored
specification (`spec/predicates/adversarial-execution-evidence.md`, in the
coordinate frame of the commit recorded in `spec/VENDOR-PIN.json`) says at
lines 296 to 307 that the producer is a substrate operator signing what the
substrate observed, and that "Verdicts (pass/fail against an organization's
policy) are deliberately out of scope; they belong in a downstream summary
predicate such as [VSA], computed over this evidence."

An evaluation record is downstream of that line. It carries a reward, a
verifier, a set of graded files and a trial identity. Folding it into AEE
version 0.8 would put a downstream verdict inside a predicate whose whole
design is that it carries observations and lets the consumer recompute. So
this contract is separate, versioned separately, and its conformance corpus
(`vectors-artifact-binding/`) is separate.

The separation is not a disclaimer of relationship. Four AEE consumer
obligations bear directly on how a consumer of an artifact-binding record must
behave, and this contract restates their shape rather than inventing a new
one:

- Lines 417 to 429: any property the recompute reads travels on the row
  itself, as a required member, fail-closed on missing or unknown values.
  This contract applies the same rule to artifact roles: a role the profile
  requires is a required member of `artifacts[]`, and its absence fails
  closed as `not-established` rather than degrading to a pass.
- Lines 1822 to 1835: a consumer MUST pin, out of band, the digests it
  expects, and an anchor-mismatched attestation is "valid evidence about the
  wrong context." A signature over this manifest says who assembled the
  record, never that the record describes the run the consumer cares about.
  The consumer pins the signer key and, where it has one, the expected trial
  identity.
- Lines 1837 to 1864: a consumer MUST pin the set of assessment classes it
  requires, because "withdrawn coverage is invisible in the carried bytes."
  The same hole exists here in a different shape: a producer that never
  captured a grading input emits a record indistinguishable from one that had
  nothing to capture. This contract closes it the same way, by making the
  required-role profile a consumer-held pin (section 6) rather than a
  producer declaration.
- Lines 1866 to 1878: a declined binding strength is never reported as a bare
  pass. A record whose dependency coverage is `incomplete` is reported as
  such and never as `verified`.

None of those four obligations covers every missing evaluation artifact,
which is why this contract carries its own required-role profile and its own
explicit `not-established` outcome.

## 2. What already exists in Harbor, and what does not

Harbor already records regrade provenance. `src/harbor/models/job/lock.py`
defines `SourceTrialLock` (class at line 91 as of harbor-framework/harbor
`1f84b4c`, 2026-09-08), carrying `action`, `type`, `trial_id` and the source
trial's own `TaskLock`, and `TrialLock.source_trial` (line 195) hangs it off
every trial lock. Line numbers here are read from that commit and no other; the
identifiers are the durable reference. `src/harbor/trial/regrade.py` refuses a regrade whose declared verifier
inputs are absent from the source trial's `artifacts/manifest.json`
(`_validate_artifact_coverage`, line 307), and distinguishes `failed`,
`skipped` and `empty` collection statuses when it does so;
`read_artifact_manifest` (line 191) refuses a missing or unparseable manifest
outright. `lock.py` also hashes files:
`_file_sha256_digest` (line 589) pins the task, extra instructions, skills and
extra compose files.

So it is false to say Harbor has no provenance. What Harbor does not have is a
binding between a result and the bytes that produced it:

- The digests in `lock.json` cover INPUTS. Nothing covers the agent
  trajectory, the collected artifacts, the reward, the verifier output or
  `result.json`.
- `artifacts/manifest.json` records that a collection was ATTEMPTED and its
  status. `ArtifactManifestEntry` carries a source, a destination, a type, a
  status and a service, and no digest and no length, so it cannot tell a
  consumer whether the bytes on disk today are the bytes that were graded.
- That absence is what stops the check one level down. At `regrade.py:361` the
  test is `if replay_path.exists(): continue`: existence at a path standing in
  for integrity. Of the four demonstrations in section 8 and in
  `demo/four-arms.sh`, Harbor already implements three, and this is the one it
  does not. Change the bytes at that path between an execute and a regrade and
  the regrade proceeds and produces a score that looks exactly as authoritative
  as one computed over the original archive.
- The equality keys on the lock models (`TaskLock._equality_key` and the
  others) are semantic input comparison for resume and cache decisions. They
  are Python tuples and they are not, and must not become, a wire-format hash
  preimage.

This contract therefore adds a record OUTSIDE the equality machinery, over
finalized persisted bytes, and changes nothing about how Harbor compares
configurations.

## 3. The manifest

A binding manifest is one JSON object. It is written after the trial's files
are final and never mutated afterwards. It does not contain its own digest and
does not contain its signature; both live beside it.

```json
{
  "schema_version": "artifact-binding/v1",
  "producer": {
    "tool": "aee-bind",
    "tool_version": "1.0.0",
    "producer_id": "example-producer"
  },
  "run": {
    "framework": "harbor",
    "trial_id": "bfca0f93-9373-4671-9197-972b61123f77",
    "trial_id_source": "result.json:id",
    "task_name": "trivial-task",
    "recorded_at": "2026-09-09T08:19:39Z"
  },
  "operation": "execute",
  "artifacts": [
    {
      "role": "trial_result",
      "path": "result.json",
      "length": 4211,
      "sha256": "..."
    }
  ],
  "source_record_digest": null,
  "source_archive_digest": "...",
  "verification_inputs": {
    "verifier_id": "trivial-task/tests",
    "verifier_digest": "...",
    "grading_inputs": [
      { "role": "verifier_files", "path": "tests/test.sh", "length": 118, "sha256": "..." }
    ]
  },
  "dependencies": {
    "status": "covered",
    "uncovered": []
  },
  "atif": {
    "present": true,
    "trajectory_id": "...",
    "document_sha256": "...",
    "pointer": { "schema_version": "artifact-binding/v1", "manifest_path": "binding/manifest.json" }
  },
  "graded_outcome": { "reward": 1.0, "source_path": "verifier/reward.txt" },
  "signer_key_id": "..."
}
```

Field by field.

`schema_version` is the version of this contract, spelled exactly
`artifact-binding/v1`. A verifier written against version 1 refuses any other
value rather than guessing forward compatibility.

`producer` names the tool and, optionally, a producer identity. It is an
assertion, not evidence; the signature is what attributes the record.

`run` carries the identity of the graded run. `trial_id` is the Harbor trial
UUID, read from `result.json`'s `id` member, and `trial_id_source` records
where it was read from so a synthetic or reconstructed record cannot be
mistaken for one that read a real trial. `recorded_at` is an RFC 3339 instant
in UTC.

`operation` is `execute` or `regrade` and nothing else.

`artifacts[]` is the covered set. Each entry has `role` (from the profile in
section 6), `path` (relative to the trial directory, POSIX separators, no `..`
segment, no absolute path, no symlink traversal), `length` in bytes and
`sha256` as lowercase hexadecimal. The list is sorted by `(role, path)` so two
producers covering the same set produce the same bytes.

`source_record_digest` is null for an `execute` record. For a `regrade` record
it is the SHA-256 of the canonical bytes (section 4) of the manifest this
record derives from. That is the lineage edge, and it is a digest rather than
a path so a moved or copied record still resolves.

`source_archive_digest` identifies the saved ARCHIVE: the entries whose roles
are `atif_trajectory`, `collected_artifact`, `trial_lock` or `trial_result`,
which is what the agent execution left behind, as opposed to what a grading
operation produced. It is the SHA-256 of the canonical bytes of that
sub-array, sorted by `(role, path)`. The restriction is deliberate. A regrade
produces a new reward, a new grading stdout and a new grading stderr, so a
digest over every covered entry would differ between two gradings of one
archive and the lineage rule in section 8 could never hold. Restricted this
way, a regrade over the same saved bytes with a different verifier carries the
SAME `source_archive_digest` as the record it derives from, and that equality
is what makes the fourth demo arm checkable: two records, two outcomes, one
archive.

`verification_inputs` names what did the grading. `verifier_id` is a
human-readable identifier, `verifier_digest` is computed over the canonical
bytes of `grading_inputs`, and `grading_inputs[]` has the same entry shape as
`artifacts[]`. A changed verifier changes `verifier_digest` and nothing else.

`dependencies.status` is `covered` or `incomplete`. It is `incomplete` when
the record names a dependency it did not cover: an external ATIF trajectory
referenced by `trajectory_path`, an image referenced by path, a continuation
segment. Each such dependency appears in `uncovered[]` with a `reference` and
a `reason`. A record with `status: incomplete` is never reported as
`verified`; see section 7.

`atif` binds the trajectory document. See section 5.

`graded_outcome` is the outcome this record binds. It is a convenience copy
and it is checked, not trusted: a verifier re-reads the reward from the
covered bytes at `source_path` and fails the record if the two disagree. That
rule is what keeps the field from being a producer assertion nobody re-checks.

`signer_key_id` is the SHA-256 of the raw 32-byte Ed25519 public key. A
consumer that pins a key compares this before it verifies anything, so a
record signed by an unexpected key is refused by identity rather than by a
signature failure that reads like corruption.

## 4. Deterministic encoding

The manifest is canonicalized with JSON Canonicalization Scheme, RFC 8785
(JCS), and the canonical bytes are what get hashed and signed. Nothing else is
a preimage: not `json.dumps` output, not a Python `repr`, not a Pydantic
model dump, and not any tuple used for equality inside a producing framework.

Concretely, an implementation MUST: serialize with UTF-8 and no insignificant
whitespace; sort object members by code-unit order of their UTF-16
representation; and serialize numbers per RFC 8785 section 3.2.2.3. This
repository already implements and tests that number serialization for the AI
Agent Action corpus (`docs/ai-agent-action-canonicalization.md`), and this
contract uses the same rule so a consumer needs one canonicalizer, not two.

A manifest whose stored bytes are not identical to their own canonical form
is refused. That check is separate from the signature check and comes first,
because a non-canonical manifest with a valid signature over its
non-canonical bytes is exactly the shape a signature-only consumer accepts and
a second implementation rejects.

## 5. Binding the ATIF document

ATIF version 1.7 (harbor-framework/harbor `rfcs/0001-trajectory-format.md`)
already provides everything this contract needs and no core field has to be
added.

- The finalized trajectory document is hashed WHOLE and appears in
  `artifacts[]` with role `atif_trajectory`. `atif.document_sha256` repeats
  that digest so a consumer can check the pointer without scanning the list.
- The producer sets root `trajectory_id` on every trajectory it emits. ATIF
  1.7 already makes `trajectory_id` the canonical per-document identifier and
  already requires it on embedded subagents; setting it on the root costs
  nothing and gives the binding a stable name for the document.
- The producer MAY put a discoverability pointer at root
  `extra.artifact_binding`, an object with `schema_version` and
  `manifest_path`. This is a breadcrumb so a tool holding only the trajectory
  can find the record. It grants no trust and a consumer MUST NOT treat its
  presence as evidence of anything. The authoritative relation runs the other
  way: from the manifest to the trajectory bytes.
- An external dependency the trajectory names and the record does not cover
  (`trajectory_path` to a file outside the covered set, an image path, a
  `continued_trajectory_ref`) is reported in `dependencies.uncovered[]`.
  Silence about an uncovered dependency is a defect in the record, not a
  smaller claim.

Version 1 adds NO per-step provenance object. Whole-document binding is the
right initial contract: it is one hash, it cannot disagree with itself, and it
is checkable by a consumer with no ATIF-specific code beyond locating the
file. Per-step commitments become justified when a consumer needs partial
disclosure, streaming verification, or independently authenticated
intermediate events, and none of those is on the table yet. A contract that
adds them before there is a consumer for them is adding a surface it cannot
test.

## 6. The required-role profile for Harbor

A profile is a named set of roles a complete record must carry. It is a
CONSUMER pin: the profile is chosen by the party doing the checking, for the
same reason AEE puts the demanded assessment classes on the consumer side
(lines 1837 to 1864). A producer that chooses its own completeness bar can
withdraw a role and still look complete.

Profile `harbor/single-step/v1` requires these roles:

| Role | What it covers | Harbor path |
|---|---|---|
| `atif_trajectory` | the finalized ATIF document | `agent/*.json` matching the ATIF schema |
| `trial_result` | the trial result record | `result.json` |
| `verifier_files` | the verifier or test files used for grading | `tests/**` of the grading task |
| `reward` | the reward the grading produced | `verifier/reward.txt` or `verifier/reward.json` |
| `grading_stdout` | grading standard output | `verifier/test-stdout.txt` |
| `grading_stderr` | grading standard error | `verifier/test-stderr.txt` |

Two roles are covered when present and are not required, because Harbor does
not always produce them: `trial_lock` (`lock.json`) and `collection_manifest`
(`artifacts/manifest.json`). A producer SHOULD cover both. Any number of
`collected_artifact` entries MAY appear.

`verifier_files` entries live in `verification_inputs.grading_inputs[]` rather
than in `artifacts[]`, because they are inputs to the grading operation rather
than outputs of the run. Every other role lives in `artifacts[]`.

A role the profile requires and the record does not carry produces
`not-established`. It never produces a pass, and it is not the same answer as
a byte mismatch.

### 6.2 The dependency-selection profile

Profile `dependency-selection/v1` covers one AI-assisted dependency change: an
agent chose or changed a dependency, checks ran over the choice, and a person
approved it. It is the evidence a reviewer of that change needs and cannot
reconstruct afterwards. The record is the same manifest as section 3, with
`run.framework` set to `dependency-selection`, `atif.present` false and
`graded_outcome` null. It requires these roles:

| Role | What it covers |
|---|---|
| `lockfile_before` | the lockfile before the change |
| `lockfile_after` | the lockfile after the change |
| `skill_instructions` | the skill or instruction file in force when the agent chose |
| `provenance_check_output` | the output of the build-provenance check over the new dependency |
| `vulnerability_scan_output` | the output of the vulnerability scan over the new lockfile |
| `approval` | the human approval, naming the approver and the `lockfile_after` digest approved |

The check definitions that produced the two outputs are covered as
`verifier_files` in `verification_inputs.grading_inputs[]`.

### 6.3 Roles pinned in force

A consumer MAY pin, per role, the SHA-256 it accepts: for this profile, the
digest of the instruction file its policy says was in force. A covered entry
for a pinned role whose `sha256` is not the pinned value fails with
`role-not-in-force`, even when every byte on disk matches the record and the
signature verifies. A record can honestly bind a change made under
instructions the consumer never approved, and binding it honestly does not
make the change acceptable. Like the profile, the pin is held by the
consumer and never read from the record.

## 7. Outcomes

A verification of a record against a directory produces exactly one of three
outcomes.

`verified`. The manifest is canonical, the signature verifies under the
expected key, every covered artifact exists at its declared path with its
declared length and digest, the profile's required roles are all present,
`graded_outcome` agrees with the covered reward bytes, and
`dependencies.status` is `covered`.

`failed`. Something the record asserts is contradicted by the bytes: a
covered artifact's digest or length differs, the manifest is not canonical,
the signature does not verify, the signer key is not the expected one, the
ATIF pointer disagrees with the hashed document, `graded_outcome`
disagrees with the covered reward, or a role pinned in force (section 6.3)
covers other bytes. A failure NAMES the artifact or the field
that failed, and it happens BEFORE any grading is re-run.

`not-established`. The record cannot be checked to a conclusion because
something required is absent rather than wrong: a required role is missing, a
covered artifact is absent from disk, or `dependencies.status` is
`incomplete`. This is the outcome AEE lines 1866 to 1878 exist to protect: a
declined or unavailable binding strength is never reported as a bare pass, and
it is equally not a report that the producer cheated.

The reference implementation maps these to exit codes 0, 2 and 3, with 1
reserved for a usage or environment error, so a script can distinguish "the
bytes are wrong" from "the record does not reach a conclusion" from "the tool
could not run."

## 8. Regrading and lineage

A regrade grades saved bytes with a possibly different verifier. It produces a
SECOND manifest with `operation: regrade`, whose `source_record_digest` is the
canonical digest of the first, whose `source_archive_digest` equals the
first's, and whose `verification_inputs` describe the verifier that actually
ran. Both records are retained. Neither replaces the other, and neither is
authoritative over the other: they are two grading operations over one
archive, and the pair is the evidence.

A lineage check over a chain of records establishes, and only establishes,
that: each record is individually `verified`; each `source_record_digest`
resolves to the record before it; and every record in the chain carries the
same `source_archive_digest`. It does not establish that either verifier is
correct, and a chain in which the reward changed is a normal, expected result
rather than a fault.

## 9. Threat model

What a version-1 record establishes, and what it does not. This table is the
honest boundary of the public claim in the header.

| Threat or question | The record establishes | It does not establish |
|---|---|---|
| Archive modified after signing | covered bytes no longer match the authenticated manifest | what the original execution did |
| Result substituted between trials | the bound trial identity, result and archive disagree | that the producer used an honest trial identity in the first place |
| Required file removed | the declared artifact set is incomplete, reported as not-established | whether the producer omitted it before signing |
| Verifier changed between gradings | two grading operations used different bound inputs over one archive | that either verifier is correct |
| Producer fabricates a coherent archive | nothing beyond an attributable assertion | genuine execution, observation completeness, or honest measurement |
| Agent tampers with the grader or the signing key | protection only where those components are genuinely outside the agent's authority | isolation, merely because a signature exists |
| Image tag or external dependency changes | only the identities explicitly captured and checked | the complete runtime environment from `lock.json` alone |
| Nondeterministic grading | the outcomes and the declared inputs, for comparison | that two gradings will score identically |
| Untrusted archive paths or symlinks | the integrity of declared bytes after safe path resolution | safe extraction, which needs independent path and extraction controls |

## 10. Conformance

An implementation conforms to version 1 when it produces the three outcomes of
section 7 for the corpus in `vectors-artifact-binding/`, whose `MANIFEST.json`
carries the expected verdict and codes for every member. The corpus covers the
four demonstration arms plus a wrong signer, a non-canonical manifest, an
incomplete dependency set and an ATIF pointer that disagrees with the hashed
document.

A verifier is OFFLINE. It reads the manifest, the signature, the public key it
was given and the files on disk, and it contacts nothing. A contract whose
checking requires a service is a contract a relying party cannot re-run in
five years, which is the whole point of writing it down.
