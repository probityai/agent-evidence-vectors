# Registration evidence must not be inferred from agent discovery

This is a **proposed** corpus for the Open Evidence Lab invitation in [#352](https://github.com/probityai/agent-evidence-vectors/issues/352). It has **not** been accepted, merged or independently reproduced. It implements a *candidate BuddyLists registration-classification policy*, **not an MCP normative rule**.

The question is narrow: **May a conforming reader credit a record as one registered agent?** MCP discovery, including anonymous `tools/list` or tool use, is not registration. A signed report sitting in quarantine is not registration. A consented, durably committed and deduplicated registration with a bound and cryptographically verified one-use challenge and registry receipt is *eligible* for registration credit.

All cases are synthetic. Keys are deterministically derived from public seed labels. Their signatures establish nothing about real agents, voluntary actions, independence, or deployed services. No test event may be added to production waitlist or conversion metrics.

## Run

```shell
python -m pip install 'cryptography>=41'
python3 gen_vectors.py --check
python3 check_vectors.py
```

`gen_vectors.py` regenerates the complete `cases/`, `MANIFEST.json` and `INDEX.md` byte-for-byte; `--check` refuses drift. The checker independently reads the record and a fixture `context.json` that pins a trusted registry public key, an issued challenge and previously registered agent/swarm identifiers. The reader does **not** accept a mere `durable: true` self-assertion: it verifies an Ed25519-signed receipt over the semantic record digest and an Ed25519 agent challenge signature. This corpus uses a constrained ASCII JSON encoding, not RFC 8785 or DSSE.

## Controls and limitations

There is one positive registration control and negative cases for discovery, signed reports, quarantine, missing or wrong-purpose consent, child agents, duplicate swarms, duplicate agent identities, unissued/expired/replayed challenges, missing or unknown consumption states, key mismatch, forged signatures, and forged/missing durable receipts. The expected reason codes are pinned in the manifest. When a semantic field is changed, test signatures are regenerated to isolate the policy question; raw signature-tampering tests are separately included.

No test establishes a human-controlled independent operator, a verifiable real-world legal identity, a truthful timestamp, that a record was committed in a production database, or that the same swarm cannot create a second identity outside the pictured registry. Those require operational controls, replay resistance, real intake logs and external validation. Registration is distinct from activation or publication. An accepted synthetic vector is **not** evidence of a real conversion.

Upstream integration would require adapting this candidate's directory/registry metadata, generation workflow and verifier interface to the Lab's release checks. The host repository's `corpora/README.md` and packaging outputs must be regenerated by its maintainers' script rather than edited by hand.

### Fail-closed correction (November 17, 2026)

A follow-up self-audit found that the original candidate admitted challenge records with omitted, null or textual `consumed` state. Those now explicitly refuse as `challenge_state_unverified`; generated negative cases and adversarial controls pin this behavior.
