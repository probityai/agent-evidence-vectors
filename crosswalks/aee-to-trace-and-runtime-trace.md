# AEE to TRACE, in-toto runtime-trace, and the Asqav compliance profile

Mapping the Adversarial Execution Evidence predicate onto the three specifications that describe the environment an agent ran in. Written 2026-09-19 against primary text, not summaries: `agentrust-io/trace-spec` at commit `98aae17`, `in-toto/attestation` at commit `6fad715`, and `draft-marques-asqav-compliance-receipts-08`, dated 31 August 2026.

Offered as a basis for collaboration. Exact figures, source paths and the command that re-derives each of them live in `aee-to-trace-and-runtime-trace.json` beside this file.

## Why this crosswalk exists

TRACE's `references` block registers a relation named `behavior-trace`, defined as "A behavioural record of what the agent did, of which this record is the environment evidence" (`spec/trace-v0.2.md` §3.1.2). Two rules govern what a verifier may do with it. The first: "A `references` entry is a pointer, not evidence. What the signature attests is that this record points there, not the truth of what it points at." The second, normative: "A verifier MUST NOT reject a record because an entry in `references` cannot be resolved, and MUST NOT treat a resolved reference as attested evidence."

So the specification names the slot our predicate fills and then rules that nothing placed in it counts. That is not a contradiction to be pointed out. It is a question with an answer, and the answer is a shape: a target that a verifier appraises under its own trust anchors, so the verifier never needs the pointer to be evidence. Section three below writes that shape out and names the artifacts that supply it.

The other two specifications bound the same territory from different sides. in-toto's `runtime-trace/v0.1` records what a monitor observed during a supply-chain operation, and records it as accesses rather than as effects. Asqav's profile re-derives a subject digest from a source host, and is explicit that this is a claim about a named range and not about what executed. Read together the three describe an environment, an access log, and a repository comparison. None of them carries a statement about the state a run left behind, made from a vantage the run could not reach. That statement is what AEE carries, and the rows below say so field by field.

## How to read the rows

Each row names one AEE term, its counterpart in each of the three specifications with a section reference, and the relation between them. `SAME` means the two terms mean the same thing closely enough that one record can satisfy both readers. `NARROWER` and `WIDER` mean the counterpart covers part of the ground or more than the ground. `NO COUNTERPART` means the specification has no term for it, and those rows are the point of the document: they are the fields a TRACE or runtime-trace implementer cannot populate today, in either direction, because the vocabulary does not exist.

A section reference is a claim about a specific commit. Every one below was read at the commits named in the header, and the JSON beside this file carries the file path and the anchor line for each.

## The row that matters most: what a `behavior-trace` reference can resolve to

| AEE term | TRACE v0.2 | in-toto runtime-trace/v0.1 | Asqav draft-08 | Relation |
|---|---|---|---|---|
| observed effect: a before-root and an after-root over a declared path scope, bound to an authority digest | `rel: behavior-trace` (§3.1.2), a registered relation whose target no verifier may read as evidence | `monitorLog.fileAccess`, a list of ResourceDescriptors recording files accessed, each with a digest | the re-derived range digest of §8.2 | All three are NARROWER than the claim, and each in a different direction. TRACE names the relation and admits no target. runtime-trace records accesses, and a set of accesses is not a statement about the state that remained. Asqav re-derives from the source host, which answers what a repository says changed rather than what a machine did. |

TRACE's rule three is usually read as a wall. It is a routing rule, and reading it that way is what makes the slot fillable without a spec change.

The rule forbids exactly one inference: from *the reference resolved* to *therefore the referenced content is attested*. It says nothing about a target that carries its own signature, because such a target does not need the reference to carry assurance. Split the two jobs and the constraint dissolves:

- The reference does identity work. It says which artifact, and the optional `digest` member makes the pointer non-substitutable.
- The target does evidence work. It is a DSSE-enveloped in-toto statement, signed by a key the subject of the TRACE record cannot reach, verified by the consumer against its own trust anchors before a single field inside it is read.

The verifier's conclusion is then never "the reference resolved, therefore the agent did X", which rule three forbids. It is "I hold an attestation that verifies under a key I trust, and this Trust Record commits to its digest, so this record and that attestation describe the same run." Rule three is satisfied because none of the evidence weight passed through the resolution. The same reasoning is already how §3.3.2 treats an external execution receipt: a receipt whose issuer key the verifier holds is checked on its own terms, and one whose key is unknown is "unverified, not invalid". §3.3.2 scopes that to receipts living inside the audit chain. The construction above is the same discipline applied to a target that lives outside the record, which is precisely what `references` addresses.

**What a TRACE implementer points at.** For an execution observed inside a containment substrate, the target is an in-toto statement carrying the Adversarial Execution Evidence predicate specified at `spec/predicates/adversarial-execution-evidence.md` in `github.com/probityai/agent-evidence-vectors`, with the conformance corpora under `vectors/` and the reference verifier `aee-verify` under `cmd/` in the same repository. The observed-effect predicate that carries a before-root and after-root pair over a declared path scope is being specified in that repository alongside this crosswalk; until its file lands, the rows above describe the shape rather than cite a path, and the JSON beside this file records which of the two states each cited artifact is in. The controlled vocabulary the labels come from is `vocabulary.yaml` in `github.com/probityai/agent-evidence-vocabulary`, CC0-1.0, where every term starts `proposed` and reaches `canonical` only when a system maintained by someone other than its author emits it.

**On the relation name.** `behavior-trace` is what the agent did. An observed effect is narrower and stronger: what changed, over what scope, witnessed from outside. A separate relation is worth registering for it, and `rel` is already open to one: TRACE's schema holds `rel` to being a non-empty string rather than to the registered list, which was a deliberate change so that "a new relation is a spec change and not also a schema change" (`CHANGELOG.md`, on the pull request that landed the block). A record carrying `rel: observed-effect` validates against `schema/trace-claim.json` today, unregistered, which is a fact established by probe rather than by reading: see the next section. So the registration request is a request for interoperable meaning, not for permission, and it belongs on the list that TRACE issue 226 keeps under its first point.

## The attack on this document

A crosswalk that only agrees is worthless, so here is a record that satisfies TRACE's `references` rules and this crosswalk's identity claim, and still misleads a reader about what executed.

**Construction.** Take the hardware example at `examples/amd-sev-snp.json`: `runtime.platform: "amd-sev-snp"`, a measurement chain, `origin` absent and therefore `self`. Add one reference entry:

```json
{ "rel": "behavior-trace", "id": "run-77", "resolver": "obs.example.com" }
```

The entry is complete. `rel` is registered, `id` and `resolver` are present, the signature covers the block under §3.2.2, and `digest` is optional: the schema describes it as the digest of the referenced object "when the producer holds it at issue time". Now sign a second record for a different execution, with a different subject, a different measurement and a later `iat`, carrying the byte-identical entry. Both validate. Both verify. No verifier may reject either for unresolvability, and the producer operates `obs.example.com`.

**Why it misleads.** Nothing in either record binds the pointer to the run. An auditor reading a hardware-attested record that also points at a behavioural record reads the composition as hardware-attested evidence of what the agent did, and rule three protects the verifier's formal conclusion without protecting that reading. At audit time the resolver serves whichever run record makes the audit clean, and serves the same one to both records. §3.1.1 forbids laundering assurance through `origin` in either direction; the juxtaposition of a strong `runtime.platform` value and an unbound `behavior-trace` pointer launders it through adjacency instead, which §3.1.2 does not reach.

**Established by probe, not by argument.** Both records validate against `schema/trace-claim.json` at `98aae17` with the byte-identical entry, while a control entry missing `resolver` is refused with "'resolver' is a required property". A further probe establishes where a producer could put a binding of its own: nowhere. The entry object sets `additionalProperties: false`, so an extra member carrying the target's commitment to this record is refused, and so is a top-level field carrying the same thing. A fourth case confirms the read path is the schema's own and not a permissive one: a record whose `origin.kind` is `log-import` while `runtime.platform` keeps a hardware value is refused, which is §3.1.1's MUST working exactly as written. The JSON beside this file carries every case, each expected outcome, and a self-contained reproduction that needs nothing from this repository beyond a checkout of TRACE at that commit.

That last result is the one to dwell on, because it decides where the fix has to live. TRACE's entry object is closed. A producer who wants the reverse binding cannot put it in the record, so it must be carried by the target. The target is ours.

**The rules that stop it.** Four, and AEE already carries two of them.

1. **Forward binding.** A `behavior-trace` or `observed-effect` entry MUST carry `digest`, over the canonical bytes of a signed attestation rather than over a log page. This extends rule four's own logic: a producer who cannot name a resolver omits the entry, and a producer who cannot hold the digest should omit it for the same reason. An unbound pointer is worse than no pointer, because it reads as one.
2. **Reverse binding.** The referenced attestation MUST commit to the Trust Record it accompanies, by that record's canonical digest or its subject digest. Without this the pointer is reusable across runs, which is the attack above and the clause TRACE issue 321 had to add for its own proposed field. It generalises to every registered relation.
3. **Vantage.** The referenced attestation's signing key MUST NOT be reachable by the subject of the Trust Record. AEE states this normatively today: the substrate observation key "MUST NOT be accessible to the subject artifact", and SHOULD be held apart from the producer's assembly plane.
4. **No credit by adjacency.** A verifier MUST NOT let the Trust Record's `runtime.platform` raise the assurance of anything in `references`. The referenced attestation earns whatever its own signature earns and nothing more. This is §3.1.1's anti-laundering rule applied on the axis §3.1.2 left open.

Rules one and two are the ones TRACE does not have. Rule three is why the target has to come from a substrate rather than from the workload's own telemetry, and rule four is why a strong environment record cannot be borrowed to dress a weak behavioural one.

## What this crosswalk does not claim

AEE detects nothing, classifies nothing, and issues no verdict. It carries what a substrate observed and whether a stranger can re-check the account.

Three limits, stated plainly. The predicate is a draft under review at in-toto rather than ratified text. It is presently exercised by a first-party implementation set, so agreement between implementations is a drift check and not independent corroboration. And this document maps specification text at three named commits: a later revision of any of the three can move a section number or fill a row marked `NO COUNTERPART`, and nothing here detects that happening. The JSON beside this file carries the commit for each side and the command that re-reads it.
