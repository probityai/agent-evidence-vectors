# Recorded sets

Bytes recorded from a live run are a different kind of member from the
generated cases elsewhere in this repository. Nobody can regenerate them; what
anybody can check is that they are still the bytes their publisher released.
This corpus gives such sets a home and a check, and it is the check a
publisher's own CI can run against the directory it keeps.

## The contract

A recorded set is a directory holding a `SHA256SUMS` file and the files it
lists. A checker answers `verified` with no codes, or `failed` with every code
below that applies:

| Code | The set draws it when |
| --- | --- |
| `sums-missing` | there is no `SHA256SUMS` |
| `sums-malformed` | a line is not `<64 lowercase hex><space><space or *><path>`, or the last line has no newline |
| `path-unsafe` | a listed path is absolute, empty, has `.` or `..` segments or a backslash, names the list itself, or repeats; or the set holds a symbolic link |
| `file-missing` | a listed file is absent |
| `digest-mismatch` | a listed file does not hash to its listed SHA-256 |
| `file-unlisted` | a file in the set is not listed |
| `sums-unpinned` | the list itself does not hash to the digest the manifest pins, so a file and its list edited together are still caught |
| `binding-malformed` | a declared binding names an unlisted file, an unknown type, or a timestamp proof whose header does not parse |
| `binding-mismatch` | an `opentimestamps-file-digest` proof's header commits to bytes other than the named subject's |

A leading `./` on a listed path is ignored. The binding check reads only the
OpenTimestamps header and the SHA-256 it commits to; it does not verify the
Bitcoin attestation or any operation after the header.

**What a verified set says, and what it does not.** It says the retained bytes
match the digests their publisher listed. It says nothing about whether what
the bytes record, a payment, a budget, a settlement or a verdict, was right.

## Members

- `sets/<name>/` holds one recorded member: `bytes/` exactly as published,
  `SOURCE.json` with the repository, commit, path, contributor and the digests
  the publisher stated in public, and the publisher's licence beside the bytes.
  Material that belongs to other authors stays as pointers in `SOURCE.json`.
- `cases/<id>/` holds synthetic members, each one mutation away from an intact
  synthetic set, generated by `gen_vectors.py`. `INDEX.md` lists every member.

The first recorded member is `hs51-set2`: the companion log, its anchor and the
settlement of the horizon-shield pilot run of 2026-10-22, contributed by its
publisher in [issue 247](https://github.com/probityai/agent-evidence-vectors/issues/247).

## Run it

```sh
pip install agent-evidence-vectors
agent-evidence-vectors recorded
agent-evidence-vectors recorded check path/to/set --member hs51-set2 --json
```

The first form judges this corpus. The second checks a directory you keep
against the list and bindings this corpus pins for a member, and exits 0 when
verified, 1 when not and 2 when it could not run. To add a set, open an issue
with the repository, commit and path; the set lands under `sets/` with its
`SOURCE.json`, and the generator refuses it unless every digest you stated
still matches.
