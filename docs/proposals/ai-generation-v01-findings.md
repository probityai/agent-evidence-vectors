# Generation predicate v0.1, revision 0.1.3: six findings and the text that closes them

These findings concern the generation predicate `https://open-fab.ai/attestation/generation/v0.1` at specification revision 0.1.3, as vendored in `vectors-ai-generation/spec-vendored/` from `Open-fab-ai/openfab` at commit `f558da05aae82a7d98f18287f2bcc17e2f1d8aee`, and its two reference implementations at the same commit: the Rust library (`src/core/provenance.rs`) and the browser implementation (`web/fabcrypto.js`, `web/ops_browser.js`). Each paragraph states what the revision says, what the implementations do, the proposed text, and the corpus members that show it. The members are in `vectors-ai-generation/`; a member graded `proposed` declares both what revision 0.1.3 says of it and what the proposal below says, and no verifier is failed on one.

**F1. The member-order rule contradicts the RFC 8785 claim, and the two implementations disagree.** The revision's envelope encoding sorts object keys "ascending by Unicode code point" and then says that, for the predicate's value domain, the encoding "coincides with RFC 8785". RFC 8785 sorts member names by their UTF-16 code units, and the two orders differ whenever one name contains a character outside the Basic Multilingual Plane and another contains one in U+E000 to U+FFFF: code-point order puts U+FF61 before U+1F600, and UTF-16 order puts U+1F600 first. The value-domain restriction is about numbers, so it does not rescue the claim, and `params` is a free-form object where such names can occur. The Rust implementation sorts with `keys.sort()`, which is code-point order; the browser implementation sorts with `Object.keys(v).sort()`, which is UTF-16 order; so for such a statement the two implementations sign different bytes. The proposal is to order member names by UTF-16 code units, as RFC 8785 does, which keeps the sentence "a conforming JCS implementation reproduces the bytes" true and matches the browser implementation already. Members `vb6ce4da91879b6b0` (signed in code-point order: valid under the revision, refused under the proposal) and `v80bef8e6efc805c4` (signed in RFC 8785 order: refused under the revision, valid under the proposal) carry the same statement.

**F2. The revision does not say what each signature covers once sign-offs exist.** The envelope encoding says the bytes the signatures cover, and that `payload_sha256` digests, are the canonical form of `statement`. Neither implementation does that when the predicate carries `signoffs`: both verify the fab signature and `payload_sha256` against the statement with `signoffs` removed, and the n-th `human-signoff` signature against the statement holding only the records before it. A verifier written from the text alone therefore refuses every attestation that carries a sign-off. The proposal is to state the coverage in the envelope encoding: the fab signature and `payload_sha256` cover the statement without `signoffs`, and the n-th sign-off signature covers the statement with the first n records, its own included. Member `vc9321aca5c878ff9` is built that way (refused under the revision as written, valid under the proposal), and member `va18c8786b0c58d4e` is built the way both implementations build it today (refused under both, because under the implementations' rule the last record is signed by nobody, which is F3).

**F3. The last sign-off record is covered by no signature, and nothing binds a record to its signer.** Under the implementations' coverage the final record in `signoffs` is in no signed preimage, and no code checks that a record's `did` equals the `keyid` of the signature at its position. A record can be appended after signing, or the last record's `name` rewritten, and both implementations still verify the attestation. The Rust trust gate counts distinct verified signing keys, which is correct, while the browser approval view and its sign-off routine count distinct `did` values from the records, which an unsigned record inflates. The proposal adds three rules to the one in F2: there is exactly one sign-off signature per record, `signoffs[n].did` is the `keyid` of the n-th sign-off signature, and N-of-M counts distinct signing keys, never records or names. Member `v6898f23bf0d63e43` rewrites the last record's name after signing, `v6bc1c5c4275d451d` appends a record with no signature, `vf1e654cbe3174418` names a key that did not sign, and `ve519b6be46ced66e` carries two records under two names signed by one key, which the proposal counts as one.

**F4. "Canonicalize the statement as parsed" does not survive a verifier that parses into types.** The revision says verifiers canonicalize the statement as parsed, so a member added after signing, an optional field serialized as `null`, or an empty array serialized where the producer omission rule says it must be omitted, is in the canonical form and changes the digest. The two implementations read "as parsed" differently, and each gets one of these wrong. The Rust verifier deserializes into typed structures and re-serializes before hashing, so an unknown member is dropped and the member added after signing verifies, while a signed `null` or empty array is dropped from the bytes it hashes and the attestation fails. The browser verifier hashes the parsed value, keeping unknown members and `null` values, but deletes an empty `acceptance` array first, so it refuses the added member and the empty array and accepts the signed `null`. This reading of the Rust path is taken from the code and serde's documented behaviour and was not executed. Members `v41ffc689ab691f38` (a member added after signing), `va8e599224ef5a13a` (`agent.id` as `null`) and `va35bcfb26910a2cb` (an empty `acceptance` array) are required rejects under the revision as written. The same gap covers duplicate member names, which the revision does not mention: member `v690a27cba702a6a1` carries `author` twice, first `human` and then `ai`, with the signature over the `ai` reading, so a parser keeping the first copy reads a human-written range; the revision leaves that indeterminate and the proposal refuses any duplicate name, as I-JSON (RFC 7493) does.

**F5. The golden vector is a canonicalization vector and cannot pass attest-only verification.** The revision pins a golden statement whose canonical form is 756 bytes with sha256 `7051cb7073a3bee0a038255fd59d4679c95443bd6a81bb92d0ff3e765713bacd`, and an independent RFC 8785 implementation reproduces those bytes exactly. The statement is not an attestation a verifier can pass, though: its `generated[0].sha256` is `"00"`, its subject carries the digest of the empty string, and its `agent.did`, `did:key:z6MkGOLDEN`, is not valid base58btc because that alphabet has no `O`. Member `ve654d0e0e28896ad` is the golden statement, graded on its canonical bytes; member `v813737ad828668c4` is the same statement with real artifact digests, signed with a published test key, and every required reject in the corpus is one change to it. A signed golden attestation from each implementation, over one statement with and without sign-offs, would give the corpus members produced by someone other than its generator.

**F6. The value domain excludes integers, the reference tests sign one, and large integers split the implementations.** The revision says the value domain "contains no floating-point numbers (strings, booleans, objects, arrays only)" and that producers must not introduce floating-point numbers. The parenthesis excludes integers too, while the Rust tests sign `params` as `{"temperature": 0}`. Above 2^53 the implementations disagree: JavaScript reads 9007199254740993 as 9007199254740992, and serde_json keeps the exact value, so they hash different bytes. Graded under the text as written, member `v6e5279605cfa8ad5` (a floating-point parameter) and member `v032d7f6446838c86` (the integer 0) are required rejects, with string-valued twins `vfe6a26f63e566bac` and `v803b44c6310c58dd`. The proposal admits integers inside the I-JSON safe range and refuses the rest: member `v7e8378a3cb6f3beb` carries 2^53 - 1 and is valid under the proposal, and member `v26773fbfe7219804` carries 2^53 + 1 and is refused under it.
